# Smoke run of the Unsloth decision-model recipe (D-01, step 3)

Goal: prove that the recipe runs end to end on this PC (install, train, calibrate, save, reload, predict on cuda and cpu). The numbers below
say nothing about the final accuracy: 200 rows and 7 optimizer steps are far too few. Synthetic data only.

## `build_dataset` report

| set | rows | decisions (total) | skipped | truncated inputs | items |
|---|---|---|---|---|---|
| train | 200 | 4000 | 0 | 13 of 200 | 200 (one item per row: the model is a Clef decision model, all questions of a row in one sequence) |
| held-out | 100 | 2000 | 0 | 1 of 100 | 100 |

`reason: None` (nothing skipped). The truncation message: "13 of 200 training inputs are longer than max_seq_length = 2048, so the end of
their state is cut". Measured on 300 train rows with `max_seq_length` 16384: 1984 to 2066 tokens per row (median 2012), 5 of 300 above
2048, none above 2066. The question block (20 questions with their criteria) is about 1900 tokens, so the state gets very little room;
the cut falls on the end of the state, which is the request and the dose sentence (keys are sorted). Use `--max-seq-length 2560` or more
for the full training (cost: a few percent of time); prediction reads up to 16384 tokens and is not affected.

## Results (smoke model, not meaningful)

- `calibrate` (held-out 100 rows, temperatures fitted by cross-fit halves): accuracy 0.786, ECE 0.098, loss 0.581. Eval loss at the end of
  the epoch 0.592, train loss 0.714.
- `predict_unsloth.py` on cuda, 100 held-out rows (every 7th row), all questions: **1593 / 2000 = 79.7 %**, ECE 0.124, 208.7 ms per row
  (median 203.9, p95 237.7; the 20 questions of a row in one call). Always answering the majority label of each question gives 84.2 %:
  the smoke model has not yet beaten the prior. Full table, confusion of `analysis` and calibration bins in
  [`unsloth-smoke-merged-heldout-limit100-stride7-cuda.md`](unsloth-smoke-merged-heldout-limit100-stride7-cuda.md) (its header line says
  "seven questions": text inherited from `zero_shot_d1.run_section`; the rows here have 20).
- Per question, model / majority: `analysis` 61 / 61, `route` 13 / 39, `dose_has_unit` 17 / 83, `auc_method` 80 / 80, `compare_pair` 88 / 88,
  `is_not_available` 91 / 91, the `asked_*` questions equal their majority (78 to 97 %). `route` and `dose_has_unit` are **below** the
  majority: after 7 steps the head is still on its starting prior for those two. This is the number to watch in the full run.

## CPU serving of the merged model

`python decision/predict_unsloth.py --model decision/models/smoke/merged --split heldout --stride 70 --limit 8 --warmup 1 --device cpu`
(float32, 12 logical cores): **12.4 s per row** (median 12.3, p95 13.5; 8 rows, 20 questions each, about 2000 tokens), model load 21 s. The
accuracy on these 8 rows (114 / 160) is the same as in the first, mistaken, run that used the GPU, so the CPU path gives the same answers.
CPU serving works but is not realistic for the harness: a benchmark turn costs one such call (two in the compare turn), about 12 s, against
0.2 s on the RTX 3060. It is acceptable only for an offline score on a few rows, or on a machine without a GPU where one wait per turn is
tolerated. A smaller question set per call or a GGUF export (not documented for the head) are the only ways to bring it down.

## Problems met and workarounds

1. **The recipe page was only available as a summary** (no column names, no `calibrate` details). The API was read from the installed
   package instead (`unsloth/models/decision.py`): `build_dataset(rows, tokenizer, model)` takes dicts with `state`, `questions`, `gold`
   as JSON text or objects, so our rows (extra columns `factors`, `label_agreement`) are accepted; a `datasets.Dataset` works because it
   iterates over dicts. `from_pretrained` on a plain LM (`unsloth/Qwen3.5-0.8B`) builds a Clef decision model with a fresh head by itself.
2. **`import unsloth` needs a visible GPU** ("Unsloth cannot find any torch accelerator? You need a GPU"), so hiding the GPU to force cpu
   fails. Also, setting `CUDA_VISIBLE_DEVICES` to an empty string from Python deletes the variable on Windows, so the first "cpu" run
   silently used the GPU (199 ms per row; caught because the run file records the model device). Workaround in `predict_unsloth.py`:
   import unsloth with the GPU visible, then set `torch.cuda.is_available = lambda: False` before `from_pretrained`; Unsloth then takes
   its own CPU path (plain transformers backbone, float32).
3. **Qwen3.5 gated-delta-net kernels on cpu**: with Unsloth imported, transformers uses Unsloth's vendored Triton kernels, which fail on a
   cpu tensor ("Pointer argument cannot be accessed from Triton"). Workaround (`_reference_gated_delta` in `predict_unsloth.py`): put the
   plain PyTorch reference functions (`inspect.unwrap`) back into `transformers.models.qwen3_5.modeling_qwen3_5`. Same answers as cuda.
4. **First training step takes 171 s** (Triton compile and autotune of the vendored kernels, cached on disk afterwards); the following
   steps take 21 s. Not a bug; a longer run amortises it.
5. `causal_conv1d` is not installed (no Windows wheel), so Qwen3.5 uses its slower PyTorch reference for the short convolution: a warning
   only; the time is in the 21 s per step.
6. 2 to 6 % of the inputs are longer than `max_seq_length` 2048 (see the `build_dataset` section); the full run needs a larger value.
7. `import unsloth` writes `unsloth_compiled_cache/` into the current directory: added to `.gitignore` with `decision/models/`.
8. With 7 steps and `logging_steps=10` the trainer logs no loss during training (only the epoch evaluation); irrelevant for the full run.
9. The dataset changed under the run (the other agent replaced `parameter_asked` by `asked_<param>` noul questions): nothing in the scripts
   names a question, they read what each row declares (tested in `tests/test_train_unsloth.py`).
